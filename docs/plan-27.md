# Plan 27: required recommendations are enforced, optional ones are not

Goal: a reviewer gap that would give a silently wrong result, a crash or a hang gets handled (or the task fails the audit); polish gaps stay optional. The real `mean` task in plan 26 skipped overflow and NaN and the auditor passed it (advisory policy). The user chose, over a strict and a fix-round design, that the reviewer tags each recommendation required or optional and only required ones are enforced.

## Spike result, reviewer side (`spike/review_probe.py`, 24 real runs, about $0.82 (round 1 $0.42, round 2 $0.40))
Four plans (`mean`, `is_even`, `join_words`, `messy`), three runs each. Bar set before each round.
- Round 1 (`probe5`: "Recommend (required): / (optional):" tags, required = silently wrong result, crash or hang on an admitted input): verdicts right (controls approve 9/9, `messy` revise 3/3 with the real errors first), tags consistent on bytes, str, generators, overflow (required 3/3) and precision (optional 3/3). Bar missed: NaN on `mean` tagged optional 3/3, one stray required on `is_even` (a missing odd-negative test), NaN on `messy` flipped between runs, `join_words` empty-string double space optional 3/3.
- Round 2 (`probe6` = probe5 + "a nan or inf result, or garbled output such as doubled separators, counts as silently wrong; a missing test on its own is never required"): verdicts same; `mean` bytes, str, generators, NaN and overflow required 3/3, precision and bool optional; `is_even` no required (3/3); `join_words` empty-string required 3/3; `messy` zero divisor and NaN required 3/3, bool optional 3/3; longest finding 393. Bar met. One departure from the bar: in one `join_words` run a bare `str` input (admitted by `list[str]`) was tagged required, which fits the definition.
- Caveats: n=3 per cell; `mean` still partly echoes hints in the text (plan 25); "required" is the model's judgement and recommendations are opinionated (for example "raise ValueError for NaN" versus "document that NaN propagates"); a `mean` run now carries 4-5 required notes.
- Real `mean` implication: with these tags overflow and NaN are required, so the plan-26 real run (which skipped both) would now fail the audit.

## Decided (not up for review)
- Option 2 of the user's choice: reviewer tags required/optional; the auditor fails on an unaddressed required note and never on an optional one. Reverses plan 26's advisory policy for required notes only.
- Wording of the review sentence is the round-2 text (`probe6`) and is not re-tuned; a later change is a new decision for the user.
- Untagged notes (and notes from plan 24 to 26 tasks already stored) keep their present meaning: "address those that fit the plan", with the existing auditor behaviour (case-21 fails, case-22 and case-23 pass).
- uv, pytest, stdlib only. TDD, one red-green-commit per behaviour, failing test shown red first (a characterisation test says it is green on arrival), never edit a passing test except via an approved edit list. Never push. Signed commits (unsigned if signing fails, re-sign at the end).

## The change
1. `review_plan.EDGE_CASE_INSTRUCTION`: its last two sentences (the plan-26 "Recommend:" sentence and the 400-character limit) are replaced by the `probe6` sentences:
   > End each edge-case gap finding with 'Recommend (required): ' or 'Recommend (optional): ' followed by one imperative sentence stating the behaviour the implementation should have (for example, 'Recommend (required): raise TypeError for bytes and add a test'). Use required when the plan would give a silently wrong result (including a nan or inf result, or garbled output such as doubled separators), a crash or a hang on an input its declared signature admits; use optional for precision, style and documentation. A missing test on its own is never required. Keep every finding under 400 characters.
2. `review_notes.NOTES_HEADING` keeps its sentence and gains: "Notes marked 'Recommend (required)' must be handled, by the recommended behaviour or an equivalent one, with a test; notes marked 'Recommend (optional)' may be skipped." The heading is inside `task.prompt`, so the implementer, the fixer and the auditor all see it; the auditor prompt itself is unchanged. If the corpus run shows the auditor ignores the heading, adding a line to `build_audit_prompt` is a separate decision (stop rule below).
3. `review_notes.capped_findings`: a note cut at `MAX_ITEM` (500) whose required tag falls in the cut-off tail keeps the tag, as `Recommend (required) [shortened]: ` followed by the head of the note, cut to fit 500 characters. A note whose tag is inside the first 500 characters is unchanged (the existing cut). Whole notes dropped by `MAX_ITEMS` (10) or `MAX_TOTAL` (4000) are still only marked by `[truncated]`; in the 24 probe runs no run reached 10 items or 1.6k characters, so this is a residual, not handled.
4. Nothing else: no schema, verdict, code path or other cap change.

## Risks
- **Reviewer recommendations can be technically wrong and a required one cannot be waived.** Checked: `math.fsum([1e308, 1e308])` and `statistics.fmean` raise `OverflowError`; `statistics.mean` and dividing each term by `n` give `1e+308`. Some probe6 runs recommend `fsum` for overflow (the optional precision note recommends it, fine). A required note pointing at `fsum` would send the implementer into failing tests or a failed audit. The only mitigation is the human at `approve`, who sees the tags but cannot edit one, only reject the plan.
- A malicious or sloppy plan can steer the reviewer into emitting "required" notes, which is now an enforcement lever; the same trust level as before and visible at `approve`.
- The tag is model judgement. A mis-tagged "required" note on a trivial plan can fail an honest change (measured only through the corpus below and the E2E).
- An implementer may handle a required note with a design the auditor does not accept as equivalent (for example documenting NaN propagation instead of rejecting it). The corpus case-26 measures one such equivalent.
- Required notes widen the diff and cost fix rounds; a task that cannot satisfy a mis-tagged required note ends in a failed audit with no automatic retry.
- Prompt text cannot be proven by unit tests; tests pin text, the corpus and E2E measure behaviour (small n).
